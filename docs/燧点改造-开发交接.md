## 1. 核心设计（务必先理解这条不变量）

> **quota 是系统唯一的内部货币；「燧点」只是 quota 的一层显示皮肤。**
> 所有入账路径只存 / 发放 quota；只在「外部法币（¥）进入系统」的边界处做一次单位转换；**绝不要把显示单位（燧点）的数值塞进被其它代码当作 quota / 美元单位使用的字段。**

由此推论：
- 凡是「走 quota」的功能（消费扣费、余额、账单、兑换码、赠送、限额）都会**自动**以燧点展示，靠的是集中的格式化函数，不需要逐个改。
- 真正需要新逻辑的只有**法币充值**这一类——因为它引入了人民币这个新单位。

### 1.1 两个相互独立的汇率

| 概念 | 配置项 | 含义 | 用途 |
| --- | --- | --- | --- |
| 充值率 | `general_setting.points_per_cny`（本次新增） | ¥1 = 多少燧点 | 仅充值时，人民币 → 燧点 |
| 消费/展示率 | `general_setting.custom_currency_exchange_rate`（已有） | 1 USD = 多少燧点 | 燧点 ↔ quota 的换算（消费、余额、到账、兑换码等全部用它） |

- 燧点 ↔ quota 的换算**全站统一**用 `custom_currency_exchange_rate`：`quota = 燧点 ÷ rate × QuotaPerUnit`。
- 人民币 → 燧点 只在充值入口用 `points_per_cny`。
- 二者独立，可分别调整；若要让「充值口径」与「消费成本口径」对齐，令 `custom_currency_exchange_rate = 业务USD/CNY汇率 × points_per_cny`（例：$1=¥7、¥1=1000燧点 → rate=7000）。

### 2.3 充值链路数据流（CUSTOM，以微信/易支付为例）
```
前端: 用户选 ¥10 (topupAmount=10)
  └─ POST /api/user/pay { amount: 10 }
后端 RequestEpay:
  payMoney = 10 (getPayMoney CUSTOM)
  points   = 10 × points_per_cny(1000) = 10000        → TopUp.Amount
  frozen   = CustomPointsToQuota(10000)               → TopUp.Quota (精确到账 quota)
  TopUp.Money = 10
支付回调 EpayNotify:
  credit = TopUp.Quota (优先)                          → 用户 quota += frozen
展示:
  订单历史 = formatQuotaWithCurrency(TopUp.Quota)      → "10,000 燧点"
  余额     = FormatQuota(user.quota)                   → 燧点
```

## 3. 本次修复的三个 Bug（务必知道成因）

1. **支付方式「最低 ¥1,000」**：`recharge-form-card` 里最低值按 `min × usdExchangeRate` 展示，而 CUSTOM 下该 rate 被复用为 `points_per_cny`(1000)，导致 ¥1 显示成 ¥1,000。修复：CUSTOM 下最低值是人民币约束，直接按 ¥ 展示，不乘率。
2. **订单显示「充值 3,500,000,000」**：订单历史用 `formatCurrencyFromUSD(record.amount)`，把存了燧点的 `Amount`(500,000) 当美元再乘一次汇率(7000)。修复：改用下单冻结的 `quota` 展示。
3. **回落超额到账隐患**：因 `Amount` 存了燧点，完成回调的回落公式 `Amount × QuotaPerUnit` 会超额到账数千倍。修复：`EpayNotify` 与 `ManualCompleteTopUp` 的回落分支在 CUSTOM 下改用 `CustomPointsToQuota(Amount)`。
4. **余额/订单显示「50,000.01」**：冻结 quota 不是 1 燧点的整数倍（¥50→quota 3,571,429→换算回 50,000.006 燧点），2 位小数把亚单位误差暴露了。修复：`lib/currency.ts` 让自定义货币在格式化层统一整数展示；内部 quota 仍保留更细精度，仅显示取整。**注意副作用**：小于 1 燧点的消费也会取整展示（见 §5.6）。

## 4. 已知设计取舍 / 坑（接手必读）

- **`TopUp.Amount` 在 CUSTOM 下存的是「燧点」，而非系统其它地方默认的「美元单位」。** 这是上述 Bug 2/3 的根因。目前通过「展示改用 `Quota`、回落分支 CUSTOM 感知」已闭合，但这是一个语义重载的脆弱点。
  - **接手建议**：新增任何读取 `TopUp.Amount` 的代码时，务必判断展示类型；或考虑重构为「`Amount` 恒为基础单位、展示与到账一律以 `Quota` 为准」，彻底消除重载。
- **`Quota` 列是到账真相来源**：完成回调一律优先用它；`Quota=0` 仅应出现在本次上线前的旧订单（那些必然是非 CUSTOM）。CUSTOM 订单在 `RequestEpay` 必然写入 `Quota>0`。
- **配置缺失保护**：CUSTOM 下若 `points_per_cny<=0` 或 `custom_currency_exchange_rate<=0`，`RequestEpay` 拒绝下单（不会创建异常订单）。

## 5. 后续待完善（有限、可枚举，非无底洞）

依据不变量核对（详见 [燧点最小实现方案.md](燧点最小实现方案.md) 附录 A），真正剩余项如下：

### 5.1 法币充值渠道（同一模式，建议统一抽象后再逐个接）
- **Stripe / Creem / Waffo / Waffo Pancake** 目前在 CUSTOM 下仍走各自单价，未燧点化（❌）。
- 建议：抽一个统一的「充值订单到账 quota 解析」函数（输入渠道金额+币种，输出冻结 quota），让各渠道 `RequestXxxPay` 在下单时写入 `TopUp.Quota`，完成回调统一发 `Quota`。这样新增渠道是「填空」，不是逐个打补丁。
- **支付宝**：由独立 Rust 项目 `model-hub-rs` 处理。**已按同一口径对齐**（Rust `create_order` 冻结 `top_ups.quota`、回调/补单按 `quota` 入账），详见该仓库 `docs/燧点-支付宝充值金额修复.md`。上线要点：Rust 与 Go 必须都部署；用**新建订单**验证（旧订单是过渡坏数据）。

### 5.2 订阅子系统（独立）
- `controller/subscription_payment_*.go`、`model/subscription.go` 为独立流程，套餐按 `PriceAmount`（视作美元）计价。
- 余额购买套餐的扣减算术与消费一致；但**套餐价展示、非余额渠道支付订阅**未做燧点审查（❌）。若上线订阅需单独一轮。

### 5.3 后台赠送/签到「录入口径」统一（⚠️，非阻断）
以下后台配置目前按**原始 quota** 录入，与兑换码/调额（按燧点录入）口径不一致：
- 新用户注册赠送 `QuotaForNewUser`、邀请人/被邀请人赠送 `QuotaForInviter`/`QuotaForInvitee`、签到奖励 `checkin_setting.min_quota`/`max_quota`、预扣 `PreConsumedQuota`。
- 建议：把这些输入框改为与兑换码一致的燧点输入（前端 `parseQuotaFromDollars` / `formatQuota`，见 `redemptions-mutate-drawer.tsx` 用法）。功能当前可用，仅体验/口径问题。

### 5.4 收尾小项
- 充值成功日志已燧点化；自定义金额输入框下可再加「获得 N 燧点」实时预览（当前预设卡片与确认弹窗已展示）。

### 5.5 余额缓存一致性（⚠️ 有条件，复审新增；补单已修）
`GetUserQuota(id, false)` 在 `RedisEnabled` 时优先读 Redis 缓存。各入账路径对缓存的处理：

| 入账路径 | 是否刷新余额缓存 |
| --- | --- |
| 真实微信/易支付回调 `EpayNotify` | ✅ 走 `IncreaseUserQuota`（含 `cacheIncrUserQuota`） |
| 补单 `ManualCompleteTopUp` | ✅ **已修**：事务提交后调用 `invalidateUserCache(userId)` 失效缓存，下次读取从库重建（仅实际到账时处理，幂等命中跳过） |
| 支付宝入账（Rust）| ❌ Rust 直接改库，无法触达 Go 的 Redis 缓存（**仍待处理**） |
| Stripe/Creem/Waffo 回调 `Recharge*` | ❌ 同为原始 `tx.Update`，未处理（境外渠道，见 §5.1） |

- 影响：**开启 Redis 余额缓存时**，未处理路径到账后页面余额可能短暂显示旧值，直到缓存过期或某次 `fromDB=true` 读取刷新。库里 `users.quota` 始终正确。
- 该问题**本次改造之前就存在**（各直接改库路径一直如此），非燧点引入。
- 补单为何用「失效」而非「增量」：`cacheIncrUserQuota` 对不存在的缓存 key 做 `HINCRBY` 会创建只含 `Quota` 字段的残缺哈希；补单是低频管理操作，直接失效、下次读重建最安全。
- 仍待处理：**Rust 支付宝入账后的 Go 缓存失效**属跨系统问题，需单独设计（如 Rust 入账后发失效信号 / Go 侧订阅 / 缩短 quota 缓存 TTL）。若生产不开 Redis 余额缓存则不受影响。

### 5.6 消费展示精度（⚠️ 取舍，复审新增）
`lib/currency.ts` 让自定义货币整数展示后，**小于 1 燧点的消费**会被取整（前端因 `adjustForMinimum` 下限为 1，会显示「1 燧点」）。在 `7000 燧点/USD` 下单次请求多为数燧点，出现概率低。后端消费日志仍用 `logger.FormatQuota`（6 位小数，如「燧点70.000000」）保留精度、未取整。
- 决策点：若要消费记录也整数、或反之要求充值/余额也保留小数，需明确「余额/充值整数、消费保留 N 位」的分档策略，再分别调整前端 `currency.ts` 与后端 `FormatQuota`。
