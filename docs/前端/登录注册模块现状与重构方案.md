# 登录注册模块现状与重构方案

## 文档信息

- 最后整理：2026-07-30
- 文档状态：P0 已实施；手机号验证码登录与可控自动注册主链路已实施，待真实短信环境联调
- 适用范围：`modelrec-new-api/web/default/src/features/auth`、Go 认证控制器与用户模型、`model-hub-rs` 短信服务
- 原型来源：[墨刀登录/注册原型](https://modao.cc/agent-py/share/6a57392b75d0275ef6ab2367/workspace/file/modelhub-platform.html/login.html?render_html=true)
- 事实依据：当前前端路由、认证组件、API 封装、Go 控制器、系统状态配置

> 本文将“当前已经实现的能力”和“计划实施的重构内容”分开描述。原型只作为视觉和交互参考，不作为后端业务契约。

## 0. 2026-07-17 实施结论

- Go 服务继续作为登录、注册、密码找回、系统状态和 Session 的唯一业务入口。
- Rust 服务不建立第二套登录态，只提供短信、阿里云验证码等专项能力；Go 通过 `MODEL_HUB_BASE_URL` 调用 Rust。
- 两个服务的当前本地配置指向同一 PostgreSQL 数据库，但认证写入和 Session 建立仍由 Go 负责，前端不能直接改用 Rust 登录接口。
- 人机验证统一为单一提供方，可在 `/system-settings/auth/bot-protection` 选择关闭、Turnstile 或阿里云验证码；阿里云验证由 Go 转发给 Rust，两种验证码不会在同一流程中连续出现。
- 注册页提供“手机号注册 / 邮箱注册”互斥切换。两种方式共用 Go 注册接口和 `verification_code` 字段，提交时只携带当前方式对应的手机号或邮箱。
- 邮箱注册仅在系统启用 `email_verification` 时展示，避免后端不保存邮箱却让用户误以为已完成邮箱注册。
- 忘记密码当前只支持已绑定邮箱找回，不增加手机号找回入口。
- 由于系统已允许纯手机号注册，手机号找回应作为后续高优先级能力；在该能力上线前，应引导手机号用户绑定邮箱，否则纯手机号用户忘记密码后无法自助恢复账号。
- 微信及既有 OAuth 继续沿用现有成熟流程；支付宝登录本轮明确延期，不新增入口、不接接口。
- 本轮所有代码先由业务方复核，不执行 Git 提交。

## 0.1 2026-07-30 手机号认证实施结论

- 已新增 Go 短信认证入口 `POST /api/user/login/sms/send` 和 `POST /api/user/login/sms`；前端登录页不再把短信验证码塞入密码字段。
- 已实现“已注册手机号直接登录、未注册手机号按开关自动创建账号并登录”，并拒绝封禁账号和软删除账号重新建号。
- 已新增 `SmsLoginEnabled` 和 `SmsAutoRegisterEnabled`，分别控制短信登录和自动注册；自动注册默认关闭，需管理员显式开启。
- 普通注册与短信自动注册已共用事务化用户创建服务，用户、邀请奖励和默认令牌在同一事务中完成。
- 手机号认证保留 2FA 分流，并在登录审计中记录认证方式、是否自动建号和是否经过二次验证；日志不记录完整手机号或短信验证码。
- Go 调用 Rust 短信服务时会转发浏览器真实 IP，Rust 已对短信发送和校验接口增加 IP 限流，并移除短信日志中的完整手机号。
- 前端已根据两个登录开关动态展示短信/密码标签，并在自动注册开启或关闭时显示对应说明；新账号成功后显示明确提示并清理已消费的邀请码。
- 当前仍需在真实阿里云环境验证验证码一次性消费语义，并补充手机号小时/天级、Session 维度和连续错误次数限制；这些内容继续作为上线前安全项。

## 1. 模块定位

登录注册模块负责访客进入系统前的身份认证、账户创建和认证方式选择，并衔接忘记密码、二次验证、OAuth 回调和 Passkey 等后续流程。

本次重构的目标不是重写认证体系，而是：

1. 参考原型统一登录、注册页面的视觉结构。
2. 保留现有成熟的后端认证能力和配置开关。
3. 修复表单中已经确认的状态、校验和交互断点。
4. 清理无效入口、注释代码和仅有界面但没有业务逻辑的控件。
5. 完善桌面端、移动端、键盘操作和错误反馈。

## 2. 原型结论

### 2.1 视觉结构

原型采用居中的左右分栏卡片：

- 左侧为绿色品牌区，包含 Logo、产品标语、数据卖点和版权信息。
- 右侧为白色表单区，顶部使用“登录 / 注册”标签切换页面。
- 主按钮使用橙色高亮，输入框使用浅灰背景和较大圆角。
- 快捷登录入口位于表单底部。
- 移动端需要将左侧品牌区收起或转换为紧凑品牌头部。

### 2.2 登录原型

登录原型包含：

- 手机号输入框
- 密码输入框
- “使用验证码登录”入口
- “忘记密码”入口
- 登录按钮
- 快捷登录入口
- 用户协议和隐私政策说明

原型没有覆盖加载状态、表单错误、密码显示、验证码倒计时、二次验证和功能开关等真实业务状态。

### 2.3 注册原型

注册原型包含：

- 手机号输入框
- 短信验证码及发送按钮
- 密码输入框
- 确认密码输入框
- 创建账户按钮
- 快捷登录入口

当前后端注册仍要求用户名，因此不能直接按照原型删除用户名，也不能在没有业务确认的情况下自动使用手机号生成用户名。

原型中的蓝色快捷登录图标没有对应到当前已确认的认证接口。重构时只展示后端真实启用的认证渠道，不增加不可用的占位入口。

### 2.4 原型本身的问题

- 页面右侧存在导出脚本文本泄漏和横向溢出，属于原型导出问题，不应复刻。
- 登录和注册页面底部使用了相同的协议文案，正式页面需要根据具体动作区分。
- 原型只展示理想状态，不能直接作为完整的交互和错误状态规范。

## 3. 当前已实现能力

### 3.1 用户可见能力

- 用户名或邮箱加密码登录
- 手机号加短信验证码登录；未注册手机号可在管理员开启自动注册后直接建号并登录
- 用户注册
- 邮箱验证码发送
- 短信验证码发送和校验
- 忘记密码及邮件重置
- 2FA 二次验证
- Passkey 登录
- 微信验证码登录
- GitHub、Discord、OIDC、LinuxDO、自定义 OAuth 等第三方登录
- 用户协议和隐私政策确认
- Turnstile 人机验证，以及配置启用后的阿里云验证码 2.0

手机号登录与自动注册由独立开关控制。已有正常账号在全局注册关闭时仍可登录；新手机号只有在 `RegisterEnabled` 和 `SmsAutoRegisterEnabled` 同时开启时才会创建账号。当前密码找回仍只支持邮箱，手机号找回尚未实现。

### 3.2 系统控制能力

认证页面需要读取 `/api/status` 返回的系统状态，主要包括：

- `register_enabled`
- `password_login_enabled`
- `password_register_enabled`
- `sms_login_enabled`
- `sms_auto_register_enabled`
- `email_verification`
- `turnstile_check`
- `human_verification_provider`
- `aliyun_captcha_enabled`
- `aliyun_captcha_region`
- `aliyun_captcha_prefix`
- `aliyun_captcha_scene_id`
- `passkey_login`
- `wechat_login`
- 各 OAuth 渠道开关及客户端配置
- `user_agreement_enabled`
- `privacy_policy_enabled`
- `self_use_mode_enabled`

当前前端类型和注册组件还读取了 `oauth_register_enabled`，但在现有 `/api/status` 返回实现中没有确认到该字段。后续实现不能将其作为可靠的唯一判断条件。

## 4. 关键入口与接口

### 4.1 前端路由

| 路由 | 作用 |
|---|---|
| `/sign-in` | 登录页，支持 `redirect` 查询参数 |
| `/sign-up` | 注册页 |
| `/register` | 注册兼容路由，重定向至 `/sign-up` |
| `/forgot-password` | 发送密码重置邮件 |
| `/user/reset` | 根据邮件令牌重置密码 |
| `/otp` | 2FA 验证页 |
| `/oauth/$provider` | OAuth 回调页 |

### 4.2 主要接口

| 接口 | 作用 |
|---|---|
| `POST /api/user/login` | 密码登录；兼容旧版手机号验证码请求 |
| `POST /api/user/login/sms/send` | 通过 Go 完成人机验证并发送登录/注册短信验证码 |
| `POST /api/user/login/sms` | 校验短信验证码，并完成已有账号登录或未注册手机号自动建号 |
| `POST /api/user/login/2fa` | 完成 2FA 登录 |
| `POST /api/user/register` | 用户注册 |
| `GET /api/verification` | 发送邮箱验证码 |
| `GET /api/reset_password` | 发送密码重置邮件 |
| `POST /api/v2/auth/sms/send` | Rust 短信发送能力；短信登录由 Go 服务端调用 |
| `POST /api/v2/auth/sms/verify` | Rust 短信校验能力；短信登录由 Go 服务端调用 |
| `GET /api/oauth/state` | 获取 OAuth CSRF state |
| `GET /api/oauth/wechat` | 微信验证码登录 |
| `POST /api/user/passkey/login/begin` | 开始 Passkey 登录 |
| `POST /api/user/passkey/login/finish` | 完成 Passkey 登录 |
| `GET /api/user/self` | 登录成功后获取当前用户信息 |

Rust `/api/v2` 提供底层短信能力，账号识别、自动注册、2FA、审计和 Session 仍统一由 Go 主服务负责。浏览器的短信登录流程只调用 Go 接口，不能自行判断手机号是否已注册。

## 5. 核心流程

### 5.1 密码登录

```text
进入 /sign-in
  → 读取系统认证配置
  → 输入用户名或邮箱、密码
  → 完成系统选定的人机验证（阿里云验证码或 Turnstile）
  → POST /api/user/login
  → 需要 2FA 时跳转 /otp
  → 否则获取 /api/user/self
  → 写入用户状态
  → 跳转 redirect 或 /dashboard
```

### 5.2 手机验证码登录

```text
进入短信登录
  → 输入手机号
  → 完成人机验证
  → POST /api/user/login/sms/send
  → Go 固定短信签名和模板并请求 Rust 发送验证码
  → 输入验证码
  → POST /api/user/login/sms
  → Go 请求 Rust 校验短信验证码
  → 已注册且正常：继续 2FA 或登录成功流程
  → 已封禁或软删除：拒绝登录且不重新创建
  → 未注册：检查全局注册与短信自动注册开关
      → 开关允许：事务创建账号、默认资源并建立 Session
      → 开关不允许：返回注册不可用
```

### 5.3 手机号注册

```text
进入 /sign-up
  → 检查注册和密码注册开关
  → 输入用户名、手机号、短信验证码、密码、确认密码
  → 勾选协议（如果启用）
  → 完成系统选定的人机验证（如果启用）
  → POST /api/user/register
  → 注册成功后返回登录页
```

### 5.4 邮箱注册

现有后端支持在提供邮箱时校验邮箱验证码，邮箱和手机号共用 `verification_code` 字段。前端现已将二者实现为互斥注册方式：切换时清空另一种身份字段和验证码，构造请求时也只提交当前方式对应的 `email` 或 `phone`。

### 5.5 阿里云验证码调用链

```text
前端读取 GET /api/status
  → 加载阿里云验证码 V3 客户端脚本并弹出挑战
  → 获得一次性 captcha_verify_param
  → 随登录/注册/邮件请求提交给 Go
  → Go HumanVerificationCheck 中间件
  → POST {MODEL_HUB_BASE_URL}/api/v2/auth/captcha/verify
  → Rust 使用服务端密钥调用阿里云验证
  → 成功后 Go 继续原业务控制器并维护 Session
```

前端只接收阿里云客户端所需的 `region`、`prefix` 和 `scene_id`。AccessKey 等服务端密钥只配置在 Rust 服务，Go 状态接口和浏览器都不得暴露。

### 5.6 密码找回现状与手机号方案

当前流程只支持邮箱：

```text
输入账号已绑定邮箱
  → 完成人机验证
  → GET /api/reset_password
  → 邮箱接收重置链接
  → 在 Go 服务完成密码重置
```

该流程无法覆盖纯手机号注册用户。推荐后续将页面改为“邮箱找回 / 手机号找回”互斥方式：

```text
手机号找回
  → 输入已验证手机号
  → 完成人机验证
  → Go 请求 Rust 发送 password_reset 用途的短信验证码
  → Go 协调 Rust 校验验证码
  → Go 签发短时、一次性的密码重置凭证
  → 用户设置新密码
  → Go 更新密码并使既有登录会话失效
```

实现时必须满足以下约束：

- Go 继续作为账号识别、重置凭证、密码修改和 Session 的唯一权威入口，Rust 不直接修改用户密码。
- 短信验证码必须按用途隔离，`password_reset` 验证码不得与注册或短信登录验证码混用。
- 发送和校验接口需要按 IP、手机号、设备及时间窗口限流，并限制连续错误次数。
- 接口返回统一模糊提示，不向未登录用户泄露邮箱或手机号是否已经注册。
- 验证码和重置凭证均应短时有效、仅可使用一次；重置成功后使其他会话失效，不自动登录。
- 在手机号找回上线前，注册成功后应引导手机号用户绑定邮箱；如果手机号注册将正式开放但不要求绑定邮箱，则手机号找回应作为发布前阻断项。

具体接口名称、验证码有效期、错误次数和会话失效范围需要在后端实现前单独确认，本文不预设尚不存在的接口契约。

## 7. 已确认问题

### 7.1 P0：重构时必须修复

| 问题 | 当前影响 | 建议处理 |
|---|---|---|
| 邮箱验证码状态与表单字段分离 | 开启邮箱验证时可能始终无法通过提交前校验 | 统一由 React Hook Form 管理 |
| 注册确认密码被注释 | 无法在客户端确认两次密码一致 | 恢复字段并使用 Zod 校验 |
| 手机号前后端规则不一致 | 前端仅接受中国大陆 11 位，后端接受 6–15 位数字 | 按确认后的业务范围统一规则 |
| “记住我”没有任何状态或接口逻辑 | 用户操作不会产生效果 | 本次移除，待会话策略明确后再实现 |
| 登录注册入口未完整遵循状态开关 | 后端禁用能力后前端仍可能展示入口 | 页面和表单都按 `/api/status` 渲染 |
| 注册组件包含大量废弃注释代码 | 增加维护和误改风险 | 删除死代码并拆分子组件 |
| 注册密码显示状态在渲染回调中调用 Hook | 违反稳定的 Hook 组织方式 | 将状态提升至组件顶层或拆分密码字段组件 |
| 注册成功存在 `window.location.href` 回退 | 绕过统一路由行为 | 使用 TanStack Router 完成跳转 |

### 7.2 P1：主流程完成后处理

| 问题 | 建议处理 |
|---|---|
| 密码显示按钮不能正常键盘聚焦 | 增加可访问名称并允许键盘操作 |
| 输入框缺少明确的自动填充语义 | 设置 `username`、`current-password`、`new-password`、`one-time-code` |
| Telegram 登录入口只有“即将支持”提示 | 功能完成前不展示入口 |
| 登录 `redirect` 接受任意字符串 | 限制为合法站内路径 |
| 错误信息主要依赖全局 Toast | 保留服务端提示，同时将字段错误关联至具体输入框 |
| 注册和登录表单过大 | 拆分模式切换、密码字段、验证码字段和快捷登录区域 |
| 纯手机号用户无法通过邮箱找回密码 | 增加手机号找回，或在手机号注册后强制绑定邮箱；正式开放纯手机号注册前至少完成其中一项 |

### 7.3 单独的后端安全项

`controller/user.go` 原短信注册校验失败日志包含手机号和短信验证码明文。本轮已移除这两个敏感字段，失败日志仅保留错误和校验结果，接口行为不变。

## 8. P0 实施方案

### 8.1 共享认证外壳

## 11. 手机号验证码登录并自动注册方案（2026-07-30 已实施）

### 11.0 实际落地范围

本轮已完成：

- Go 短信发送、短信认证、旧登录接口兼容、2FA pending 信息和结构化登录审计。

### 11.1 目标与范围

目标行为如下：

- 手机号已注册：验证码正确后直接登录。
- 手机号未注册：验证码正确后自动创建账号并登录。
- 手机号对应账号已封禁或已注销：禁止登录，也不得创建重复账号。
- 关闭自动注册后：已有手机号仍可登录，新手机号不能建号。
- 保留现有密码登录、邮箱注册、手机号注册、OAuth、Passkey 和 2FA 流程。
- 第一阶段继续只支持中国大陆手机号，不在本次同时引入国际手机号。
- 暂不增加通用身份表，继续复用现有 `users.phone` 和 `phone_verified` 字段。
- Go 继续作为用户、注册副作用、2FA、审计和 Session 的唯一权威入口；Rust 只提供短信发送与校验能力。

前端不得先调用公开接口判断手机号是否注册，再分别选择登录或注册。账号识别必须发生在短信验证码校验后的 Go 服务内部，避免泄露手机号注册状态，并防止前后端产生竞态。

### 11.2 行为矩阵

| 账号状态 | 短信登录 | 全局注册 | 自动注册 | 结果 |
|---|---:|---:|---:|---|
| 已存在且正常 | 开 | 任意 | 任意 | 登录 |
| 已存在且正常 | 关 | 任意 | 任意 | 拒绝短信登录 |
| 不存在 | 开 | 开 | 开 | 创建账号并登录 |
| 不存在 | 开 | 关 | 开 | 拒绝创建 |
| 不存在 | 开 | 开 | 关 | 拒绝创建 |
| 已封禁或已注销 | 开 | 任意 | 任意 | 拒绝且不重新创建 |

`PasswordRegisterEnabled` 只控制密码注册，不控制短信自动注册。`RegisterEnabled` 继续作为所有新用户创建方式的总开关。

### 11.3 已落地流程

```text
输入手机号
  → Go 校验手机号、人机验证和发送限流
  → Go 固定短信签名与登录/注册模板并请求 Rust 发送短信
  → 用户提交手机号和短信验证码
  → Go 请求 Rust 校验短信验证码
  → 校验失败：返回统一验证码错误，不查询或创建用户
  → 校验成功：Go 使用 Unscoped 按手机号查询用户
      → 正常账号：检查状态和 2FA，建立 Session
      → 封禁或已注销账号：拒绝登录，不重新创建
      → 账号不存在：检查 RegisterEnabled 和 SmsAutoRegisterEnabled
          → 不允许注册：返回注册不可用
          → 允许注册：事务创建用户及初始化资源，随后建立 Session
  → 返回 account_created 和 onboarding_required
```

### 11.4 接口契约

#### 11.4.1 发送短信验证码

已新增 Go 接口：

```http
POST /api/user/login/sms/send
```

请求体：

```json
{
  "phone": "13800138000"
}
```

人机验证参数继续使用现有查询参数：

```text
?turnstile=...
?captcha_verify_param=...
```

成功响应：

```json
{
  "success": true,
  "message": "",
  "data": {
    "cooldown_seconds": 60
  }
}
```

浏览器不再传入 `sign_name` 和 `template_code`。Go 固定短信签名和登录/注册模板，再以服务端请求调用 Rust，防止调用方从该入口切换到修改手机号、重置密码或绑定手机号等模板。Rust 当前校验 DTO 尚无独立 `purpose` 字段，因此用途隔离仍需在扩展其他短信认证场景前补齐。

#### 11.4.2 完成短信认证

已新增 Go 接口：

```http
POST /api/user/login/sms
```

请求体：

```json
{
  "phone": "13800138000",
  "verification_code": "123456",
  "aff_code": "ABCD"
}
```

`aff_code` 可选，仅在创建新账号时使用；已有账号登录时忽略。

普通成功响应：

```json
{
  "success": true,
  "message": "",
  "data": {
    "id": 123,
    "username": "u_k4m8x2r9",
    "display_name": "用户_k4m8",
    "role": 1,
    "status": 1,
    "group": "default",
    "auth_method": "sms",
    "account_created": true,
    "onboarding_required": true
  }
```

需要 2FA 时保持现有响应结构：

```json
{
  "success": true,
  "message": "需要二次验证",
  "data": {
    "require_2fa": true
  }
}
```

已落地的稳定业务错误码：

| 错误码 | 场景 |
|---|---|
| `SMS_LOGIN_DISABLED` | 管理员关闭短信登录 |
| `SMS_CODE_INVALID_OR_EXPIRED` | 验证码错误或过期 |
| `REGISTRATION_DISABLED` | 手机号不存在，但当前不允许注册 |
| `ACCOUNT_UNAVAILABLE` | 账号封禁、注销或状态异常 |
| `SMS_SERVICE_UNAVAILABLE` | Rust 或阿里云短信服务不可用 |

错误文案由后端 i18n 提供。验证码校验成功前，不返回“手机号已注册”或“手机号未注册”等可用于账号枚举的信息。

#### 11.4.3 旧接口兼容

现有 `POST /api/user/login` 至少保留一个版本的手机号兼容逻辑，避免旧前端立即失效：

- 先解析登录方式，再判断相应开关，不能在入口处统一受 `PasswordLoginEnabled` 拦截。
- 手机号请求受 `SmsLoginEnabled` 控制，内部复用同一个手机号认证服务。
- 新前端只调用 `POST /api/user/login/sms`，不再把短信验证码放进 `password` 字段。
- 兼容期稳定后，再评估移除旧登录接口中的手机号分支。

### 11.6 后端职责与事务

已新增独立业务服务，避免继续把逻辑堆入 `controller/user.go`：

- `PhoneAuthService`：手机号规范化、短信验证码校验、用户查询、开关判断、账号状态判断和 2FA 分流。
- `UserProvisioningService`：统一新用户创建及额度、邀请、默认配置和默认令牌初始化。

`UserProvisioningService` 首先由普通注册和短信自动注册共用。OAuth、微信等注册方式可在后续单独迁移，避免本次扩大回归范围。

短信验证码校验属于外部调用，不放进数据库事务。验证码成功后再开启事务：

1. 使用 `Unscoped` 再次按手机号查询，包括软删除账号。
2. 账号不存在时创建用户并写入手机号验证状态。
3. 初始化新用户额度、邀请关系和关键用户设置。
4. 创建默认令牌。
5. 提交事务。

用户、额度、邀请计数和默认令牌必须保证全部成功或全部失败。非关键审计日志可以在事务提交后写入，但不得因日志失败向客户端错误地报告账号创建失败。

手机号唯一索引作为并发建号的最终保护。如果两个请求同时创建同一手机号：

- 只允许一个请求创建成功。
- 另一个请求捕获唯一约束冲突后重新查询用户。
- 不得重复发放额度、邀请奖励或默认令牌。

### 11.7 自动创建账号规则

当前自动账号使用以下结构：

```text
username: u_<随机 12 位字符>
display_name: 与随机内部用户名一致
password: 空
phone: 已验证手机号
phone_verified: true
role: 普通用户
status: 启用
```

约束如下：

- 不使用完整手机号作为用户名或显示名称。
- 用户名不得超过现有 20 字符限制。
- 使用密码学安全随机数生成内部用户名，数据库唯一约束作为最终保护；极低概率的随机用户名冲突当前会返回创建失败，后续可补有限次数重试。
- 空密码表示尚未设置密码；已有个人资料接口允许空密码账号首次设置密码。
- 新账号获得与普通注册一致的默认额度、邀请奖励、用户设置、侧边栏和默认令牌。
- 注册来源通过结构化审计记录为 `sms_auto_registration`，日志中不记录完整手机号和验证码。

首次登录后采用非阻断引导，建议提示用户：

- 修改用户名和显示名称。
- 绑定邮箱。
- 设置密码。
- 添加 Passkey 或 2FA。

### 11.8 Session、2FA 与审计

登录公共逻辑应接收明确的认证元数据，而不是只根据请求路径推断认证方式：

```go
type LoginMeta struct {
    Method         string
    AccountCreated bool
}
```

短信认证设置 `Method=sms`。已有账号启用 2FA 时，在 pending Session 中额外保存 `pending_login_method=sms`；2FA 完成后的审计应表达为短信认证叠加 2FA，而不是只记录 `2fa`。

认证日志禁止记录：

- 完整手机号。
- 短信验证码。
- 包含验证码的请求体。

允许记录用户 ID、认证方式、是否自动建号、IP、User-Agent、手机号掩码或不可逆哈希。

登录页需要完成以下调整：

- 只有短信可用时默认短信，只有密码可用时默认密码；两者都不可用时展示可用的 OAuth、Passkey 或不可登录提示。

- 自动注册关闭时显示“仅支持已注册手机号登录”。

- 新账号登录成功后根据 `account_created` 显示明确成功提示；接口同时返回 `onboarding_required`，完整资料完善引导留待后续页面承接。

### 11.10 手机号、验证码与限流安全

本阶段统一使用中国大陆手机号规则：

```text
^1[3-9]\d{9}$
```

上线前必须检查数据库是否存在非 11 位手机号。当前前端和 Rust 使用 11 位规则，但 Go 历史上接受 6～15 位数字，不能未经检查直接收紧后端规则导致老用户无法登录。国际手机号后续按 E.164 单独设计。

目标发送限流：

- 同一手机号 60 秒一次、每小时最多 5 次、每天最多 10 次。
- 同一 IP 每小时最多 20 次。
- 同一浏览器 Session 每小时最多 10 次。
- 保留阿里云自身发送间隔作为最后一层保护。

目标校验限制：

- 单个验证码最多允许 5 次错误。
- 超过次数后锁定该验证流程。
- 校验接口增加手机号、IP 和 Session 组合限流。
- 确认阿里云在校验成功后是否自动使验证码失效；如不会失效，增加短期一次性消费记录。
- 目标上登录/注册验证码必须与找回密码、绑定手机号隔离；当前只固定了发送模板，Rust 仍需增加显式 `purpose` 契约后才能承载其他短信用途。

当前实际状态：Go 两个短信入口继续受 `CriticalRateLimit` 的客户端 IP 限流保护；Rust 对 `/auth/sms/send` 配置为同 IP 300 秒最多 3 次，对 `/auth/sms/verify` 配置为同 IP 300 秒最多 10 次。Go 会通过 `X-Forwarded-For` 传递其确认的客户端 IP，避免所有请求聚合到 Go 服务 IP。阿里云发送接口仍设置手机号发送间隔。手机号小时/天级、Session 维度、连续错误次数和一次性消费记录尚未落地，不能把当前状态描述为已完成全部多维限流。

人机验证应在发送短信前完成，避免短信费用攻击。提交短信登录时依靠短信验证码、失败次数和组合限流，不应要求用户连续完成第二次人机验证。

### 11.13 发布、监控与回滚

推荐发布顺序：

1. 检查现有手机号格式、重复值和软删除冲突。
2. 先发布 Go 接口和配置项，保持自动注册默认关闭。
3. 发布 Rust 短信限流和必要的用途隔离。
4. 发布前端并切换到新短信认证接口。
5. 验证已有手机号登录、2FA、验证码失败和开关组合。
6. 小范围开启 `SmsAutoRegisterEnabled`。
7. 观察短信费用、新增用户数、验证码失败率和并发错误后全量开启。

建议监控短信发送成功/失败/限流次数、验证码成功/失败/过期次数、短信登录成功次数、自动创建用户数和注册事务失败数。监控标签不得使用完整手机号。

紧急回滚时优先关闭 `SmsAutoRegisterEnabled`，已有手机号仍可继续短信登录。已经创建的账号不自动删除、不回收额度；异常账号需要另行审计后处理。旧登录接口在兼容期内继续可用，便于前后端分步回滚。

### 11.14 验收标准与当前结论

- 用户无需预先判断手机号是否注册过。
- 手机号和短信验证码只提交一次即可完成登录或注册。
- 新用户获得与普通注册一致的额度、邀请奖励、默认配置和默认令牌。
- 任意并发情况下，一个手机号最多对应一个账号。
- 密码登录、短信登录、密码注册和短信自动注册开关彼此独立。
- 封禁和注销账号不会被自动重新创建。
- 短信发送已具备人机验证和 Go/Rust 两层 IP 限流；手机号小时/天级和 Session 多维度限流仍是上线前待办。
- 日志、响应和公开接口不泄露短信验证码及未经验证的手机号注册状态。
- 现有密码、邮箱、OAuth、Passkey 和 2FA 流程不受影响。

除明确标注的安全加固和真实短信联调项外，手机号“登录或自动注册”的应用主链路已完成。正式开启 `SmsAutoRegisterEnabled` 前，仍应完成存量手机号数据检查和真实短信环境验收。

## 12. 部署与联调配置

管理端入口为 `/system-settings/auth/bot-protection`。页面负责保存以下非密钥配置：

- 人机验证提供方：关闭、Cloudflare Turnstile、阿里云验证码三选一。
- Turnstile：Site Key、Secret Key。
- 阿里云验证码：区域、Prefix、SceneId。

配置写入 Go 服务的系统选项表，保存后立即更新运行时并刷新 `/api/status`。阿里云 AccessKey、AccessKey Secret 等服务端密钥仍只配置在 Rust 服务，不进入 Go 数据库，也不会返回浏览器。

环境变量保留为首次启动和旧部署的兼容方式；数据库中已保存的后台配置优先生效：


```dotenv
MODEL_HUB_BASE_URL=http://127.0.0.1:8080
HUMAN_VERIFICATION_PROVIDER=aliyun
ALIYUN_CAPTCHA_ENABLED=true
ALIYUN_CAPTCHA_REGION=cn
ALIYUN_CAPTCHA_PREFIX=实际客户端 Prefix
ALIYUN_CAPTCHA_SCENE_ID=实际场景 SceneId
```

只有 Go 与 Rust 都完成真实配置后，才能验收阿里云弹窗、一次性参数校验、失败重试和登录/注册完整链路；本地单元测试不能替代真实阿里云联调。

### 12.1 验证码显示条件

前端以 `/api/status` 为准选择一种人机验证方式：

- `human_verification_provider=aliyun` 且 `aliyun_captcha_enabled=true`，同时 `region/prefix/scene_id` 完整时，使用阿里云验证码。
- 阿里云验证码使用 popup 模式，页面上不会常驻显示验证码组件；用户点击登录、注册、发送邮箱验证码或发送重置邮件时才弹出挑战。
- `turnstile_check=true` 且配置了 `turnstile_site_key` 时，才显示常驻的 Turnstile 组件。
- 两种方式都未开启时，提供方为 `none`，页面不会出现人机验证。
- 如果 `/api/status` 中新增的 `human_verification_provider`、`aliyun_captcha_*` 字段缺失或为 `null`，应先确认 Go 服务是否已经重新编译并重启，而不是先修改前端展示条件。

### 12.2 微信快捷登录显示条件

微信快捷登录由系统配置动态控制，前端不会展示未启用的占位入口：

- 管理端需要先配置 `WeChatServerAddress`；后端在该值为空时会拒绝开启 `WeChatAuthEnabled`。
- 建议同时配置 `WeChatServerToken` 和 `WeChatAccountQRCodeImageURL`，确保验证码校验与扫码引导完整。
- `/api/status` 返回 `wechat_login=true` 后，登录页和注册页才会显示微信快捷入口。
- `wechat_login=false` 时隐藏入口属于预期行为，不是前端渲染故障。
